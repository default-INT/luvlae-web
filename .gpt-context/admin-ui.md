# Admin interface

Implemented 2026-10-18 in `apps/web` using the existing commerce APIs. Direct entry: `/admin` redirects to `/admin/orders`; there are no admin links on the public storefront.

- `/admin/login`: email/password form, generic invalid-credential error and rate-limit feedback; no registration/password-reset UI. Existing operational administrator commands remain the account setup/reset path. Never put credentials in context notes.
- Admin data uses client-side `fetch` with no-store: session, order/product lists and details load through `/api/admin/**`. `AdminSession` gates the interface using `/auth/me`; every data/mutation endpoint independently validates authorization. Route components only compose the shell/dictionary; there are no admin SSR database loaders. Storefront product and customer order SSR remain unchanged.
- Admin session cookie is now `luvlae_admin_v2`, Path=/, HttpOnly, SameSite=Strict, Secure on HTTPS, eight hours. Root path is required for both SSR `/admin` and `/api/admin`. Older API-only cookies require signing in again. Logout revokes the DB session and clears the new cookie.
- Orders show independent order/payment/fulfillment tags, newest-first cursor pagination, literal order-number search, status filters, inclusive UTC date bounds, reset and empty states. List API accepts `q`, `from`, `to` in addition to the previous status/cursor filters. Values are validated and regex search input is escaped.
- Orders open in a right-side native modal Drawer for both viewing and editing. `/admin/orders?order=:id` preserves list filters/pagination; legacy `/admin/orders/:id` redirects to it. Native History API updates selection/filters without RSC requests. Escape/backdrop/close dismiss the Drawer, focus is trapped, and dismissal is blocked during saves. Saves reload details and the current filtered list through fetch. Resource reads cancel/ignore stale responses and show loading/error/retry feedback; 401 redirects to login.
- Order detail includes immutable item/pricing snapshots, customer/address, tracking and cancellation reason. Actions follow BE transitions: processing → shipped (carrier/tracking required) → delivered; separate cancellation with reason; bounded explicit restocking with a sellable-return checkbox for shipped goods. Payments cannot be arbitrarily marked paid or refunded through this UI.
- Product editor supports name, short description, USD price, total stock and sales-enabled flag, with reserved/available stock shown separately. Price parsing preserves integer cents. SKU remains immutable. Mutations require version, stable operation ID across uncertain retries, and reasons where required by BE. Version conflicts reload current data before retry.
- `_pages/admin` owns page UI, common styles, status tags and client API/mutation helpers. SCSS Modules reuse existing Manrope/navy/pale-blue tokens, cards, rounded controls and responsive layouts. Copy is in the YAML `admin` section.
- All admin pages are explicitly dynamic and noindex; private routes have no-store/CDN no-store headers and are excluded from sitemap. No new administrator account or live payment integration was introduced.
- Verification covers configured-account login, filters, order Drawer, product list/editor and no public admin links. Unit/integration checks cover escaped filters/UTC ranges, Drawer URL state, cancellable client requests, exact cents, session scope/expiry, stock/mutation invariants and storefront SSR/cart behavior. No real shipment or email is triggered by these checks.
- Stage login investigation: `b593d7b` passed local workerd login/session checks, but remote stage `luvlae-web-stage.evgeniy-trofimov-int.workers.dev` returned product API 200 and login 500 even for an unknown account. Native PBKDF2/600,000 exceeds the deployed 100,000-iteration cap, which local workerd overrides ([Cloudflare #7550](https://github.com/cloudflare/workerd/pull/7550)); the remote exception stack was unavailable. Do not treat local workerd success as proof of deployed KDF compatibility. API 5xx logging retains allowlisted exception categories (including NotSupportedError) and numeric MongoDB codes without raw messages/stacks/secrets.
- User-approved fix: standard PBKDF2-HMAC-SHA256 via `node:crypto`, 100,000 iterations, random 16-byte salt, 32-byte key and constant-time comparison. New/reset passwords and unknown-account work share this cost. Legacy 600,000-iteration or malformed hashes return false without invoking unsupported KDF work. The user will recreate administrators; the existing reset-password CLI can instead replace each hash and revoke sessions without losing account IDs. No database changes or remote deployment are performed automatically. See [authentication runbook](../apps/web/docs/commerce-api.md#protocol-and-authentication) for the platform cost tradeoff and tests.
